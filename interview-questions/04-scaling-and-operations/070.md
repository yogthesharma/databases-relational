# Question 070: Autovacuum Tuning for a Hot Table

## Context
One table receives heavy updates to a small hot subset of rows. Dead tuples accumulate; query plans degrade; autovacuum runs but "never catches up." `n_dead_tup` stays high in `pg_stat_user_tables`.

## Interviewer Prompt
1. Explain what autovacuum is trying to accomplish on this hotspot.
2. Which knobs (scale factors, cost limits, table-level storage params) would you consider first?
3. When do you split hot columns / use fillfactor / rethink the data model instead of tuning vacuum?
