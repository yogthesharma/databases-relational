# Question 011: Set-Based Updates vs Row-by-Row Anti-Patterns

## Context
A nightly job "syncs" prices from a staging table. The current implementation loops in application code:

```text
for each row in staging_prices:
  UPDATE products SET price = ... WHERE sku = ...
```

It takes 45 minutes for 2M SKUs and holds long transactions. Staging table:

```sql
CREATE TABLE staging_prices (
  sku   text PRIMARY KEY,
  price numeric(12,2) NOT NULL
);
```

## Interviewer Prompt
1. Redescribe this as a set-based SQL operation and explain why it usually outperforms row-by-row clients.
2. How would you batch the work to avoid a multi-hour transaction and lock pain while remaining set-oriented?
3. What failure modes (partial apply, retries, idempotency) must the design address?
