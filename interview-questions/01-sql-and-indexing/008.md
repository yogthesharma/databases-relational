# Question 008: CTE Materialization and Optimization Fences

## Context
A service ships this query after a refactor that wrapped intermediate steps in `WITH` clauses for readability:

```sql
WITH recent AS (
  SELECT * FROM orders WHERE created_at > now() - interval '7 days'
),
filtered AS (
  SELECT * FROM recent WHERE merchant_id = $1
)
SELECT *
FROM filtered
ORDER BY created_at DESC
LIMIT 20;
```

Latency differs sharply from the equivalent nested query without CTEs. On some major versions the CTE appears to act like an optimization fence; an engineer toggles `MATERIALIZED` / `NOT MATERIALIZED` experimentally.

## Interviewer Prompt
1. Describe how PostgreSQL may treat CTEs as optimization fences and what changed across major versions (especially around automatic inlining).
2. For this query, when would you force materialization vs inlining, and how would you prove it with `EXPLAIN`?
3. What readability vs performance guideline would you set for the team writing CTEs in application SQL?
