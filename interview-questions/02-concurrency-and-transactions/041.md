# Question 041: Repeatable Read Anomalies in Inventory

## Context
Under `REPEATABLE READ`, a transaction reads stock quantity, performs business logic, then writes. Concurrently another transaction commits a stock change. The first transaction may hit a serialization failure on write—or, depending on pattern, still surprise engineers used to `READ COMMITTED`.

## Interviewer Prompt
1. Explain snapshot behavior for reads in `REPEATABLE READ` versus `READ COMMITTED`.
2. What write conflicts surface as errors the application must retry?
3. For inventory decrement, which isolation level + locking combo would you standardize on?
